# Build 4000014: app-private renderer communication backing

The integrated engine passed physical ARM64 iOS compilation and its audited
source/dependency closure in run 37176578369 at source
`f3587da0d0bb97508fa3170386547b746d2b6324`. Final host packaging and a phone result
are pending. Do not treat this document as a published or passing phone build.

The pinned renderer's Darwin anonymous-file implementation uses named POSIX
shared memory. It optionally accepts an app-group namespace. A normal app's
writable data directory is a separate facility. The new adapter selects an
explicit app-owned file directory for renderer communication instead of
requiring named POSIX shared memory or new signing entitlements. This changes
file backing, not the Linux kernel, FEX, graphics protocol or OS architecture.

`Engine/PrivateSharedFile.h` opens a checked absolute directory with
O_NOFOLLOW/O_DIRECTORY, verifies owner and mode 0700, atomically creates a
random exclusive mode-0600 file with close-on-exec, and unlinks its name before
returning the fd. Existing upstream ftruncate/mmap and error returns remain.
The fresh host creates a unique renderer subdirectory in its new diagnostic
run directory, checks its ownership/mode and selects it before QEMU starts.
Directory failure stops bring-up. The renderer records open success/failure
without publishing host paths. No allocation failure is converted to success.

Native renderer run 37176336596 at source
`16b06b30619acf2689e4fcee49c64428481566d9` passed actual Darwin tests using the
patched upstream `os_create_anonymous_file` function, then compiled the ARM64
iOS renderer. Tests covered 256-byte, 16 KiB, 720p-buffer-size and 16 MiB files,
shared alias visibility after closing fd copies, unlinked lifetime, close-on-
exec, file permissions, invalid size, relative/missing directory, final-component
symlink and insufficiently private directory rejection. The actual iOS library
contains the private-file adapter markers. Complete original source, helper,
patches, tests and build recipes are retained in corresponding-source archives.

The required new `private_file_backing` receipt distinguishes this deliberate
allocation-policy change from build 4000013's failure-only instrumentation.
It records native hosted test success and keeps phone testing/Metal import
false. The existing diagnostic patch's own allocation-policy field remains
false because that patch only logs failures; it is not the overall build policy.

This is a communication-memory adapter. Regular file mappings may have different
storage/paging costs from an anonymous shared-memory object; measure allocation,
dirty memory, memory pressure and sustained throughput on the phone before
claiming a performance improvement. It does not implement GPU image import,
zero-copy presentation or a game frame. The 256-byte allocator test does not
measure a SteamOS memory budget.

Next acceptance is actual integrated engine/host Release compilation, unchanged
shader/report rejection checks, exact framework/payload/source/package verification
and independent public IPA download. Then a fresh phone report must show the
private backing path, context result and guest Vulkan/shader evidence. Even guest
pixels would leave independent host Metal completion/import and moving game
presentation open. No architecture substitution or complete SteamOS/game result
is claimed. The [DroidDeck blueprint](DROIDDECK-BLUEPRINT.md) remains the component
plan after the graphics gate.
