# Build 4000023: eight distinct Linux frames, separate GPU/display acceptance

This adds a bounded eight-frame guest producer and a separate native import/
screen receipt. It does not replace the requested Linux environment architecture
or weaken the original two-image display gate. Phone verification is pending.

The ARM Linux program renders eight immutable 1280x720 images with phases
0,17,34,51,68,85,102,119. Each image has a distinct exported DRM resource, a
completed producer fence, external queue ownership release and a linear BGRA
layout. The guest checks all eight rendered images: 7,372,800 pixels, checksum
5,157,519,360. Eight native buffer aliases and eight screen GPU completions must
join those exact identities. Only the first/last images have full native source
readbacks: 1,843,200 pixels, checksum 1,281,269,760. The middle images have explicit
pixel_verification_performed=false, pixels_checked=0 and channel_sum=0; their
layouts/identities and screen GPU work are checked. No host-generated pattern
or host animation of the older two images supplies the sequence.

GPU sequence acceptance and actual display timestamp acceptance are separate.
gpu_sequence_verified can pass with presentedTime=0 while presentation_verified
remains false. Positive ordered actual callback timestamps are still required
for the latter. CPU callback clocks, a later API query, screenshots and GPU
durations cannot supply display timing. The original two-image receipt stays
unchanged and strict. Unsupported animation, pacing, zero-copy and game flags
remain false in both receipts. Backgrounding, geometry/device changes, wrong
sources/formats, missing completion joins or ownership errors reject the run.

Each guest frame has a minimum 125ms diagnostic dwell; the actual interval also
includes Linux/QEMU/GPU work. This is not an FPS benchmark, a refresh-rate target
or a steady-state mutable-buffer protocol. Approximately 29.5MB of image pixels
are kept immutable until cleanup; actual allocation overhead is recorded in
guest/native receipts. The host allows one screen consumer in flight and two
drawables, with no drawable CPU readback or GPU waits on the main thread.
