# Build 4000021: visible Linux image presentation

The fresh ARM64 iOS host now has a CAMetalLayer screen, a serial GPU consumer and
separate command-completion and actual drawable-presentation receipts. It samples
the real imported guest texture after the existing source-pixel check. It does
not generate a host substitute or display the diagnostic readback buffer.

## Source scope and acceptance

The exact build4000020 Linux/engine/observer dependencies are reused. The two
immutable guest resources, phases 0 and 41, remain independent and their pixel,
format/layout, producer fence, device, native ownership and release requirements
are retained. A new linux_screen report must pass the preserved controls and
both actual screen consumers. Each frame requires its joined resource/generation,
positive ordered GPU/display timestamps, a real drawable and an unchanged visible
surface. Only one screen consumer may be in flight. Drawable allocation, rendering,
presentation callbacks or foreground/geometry failures cannot fall back to success.

Borrowed textures are retained by both GPU and drawable handlers even if the
bounded five-second wait times out. Recovery and per-stage durable capture remain
active. No automatic report upload is added. Retained context and engine state
are process-scoped; each new Linux boot requires relaunch and JIT.

Apple documents the actual [presentation callback](https://developer.apple.com/documentation/metal/mtldrawable/addpresentedhandler(_:))
and the [presentation timestamp](https://developer.apple.com/documentation/metal/mtldrawable/presentedtime).
A zero presentedTime indicates a drawable that was not shown or a dropped frame.
Drawable IDs may be reused by the owner; distinct guest resources and frame order,
not a fabricated unique drawable ID, decide the two-phase join.

## Current limits

This presents two changing test images, not continuous animation, the SteamOS
desktop or a game. Source textures are rendered into a drawable with letterboxing;
there is no drawable CPU readback. The two source-pixel GPU readbacks remain
correctness checks. End-to-end zero-copy, mutable-buffer frame synchronization,
WSI/compositor, pacing, rotation/recovery under motion and game FPS are unfinished.
The guest's intentional waits and the diagnostic callback waits are not a game
benchmark. QEMU TCG remains software CPU/system emulation.

## Owner procedure after a verified package is published

1. Install build4000021 through iLoader; close and relaunch the app.
2. Enable JIT in StikDebug and pass the ARM64 JIT check.
3. Tap Show Linux-rendered images, then Start Linux screen test. Do this as the
   first Linux boot in this process. Keep the screen foreground and avoid rotation.
4. Expect two different coloured images with letterboxing; they are generated
   inside Linux. Keep the app open until it finishes, up to three minutes.
5. Share screen-test report. If it closes, reopen and share saved recovery logs.
