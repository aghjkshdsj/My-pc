The same pinned MoltenVK revision and dependencies are used. A small scoped
patch includes fresh MIT observer headers in the actual
`MVKQueueCommandBufferSubmission::commitActiveMTLCommandBuffer` path, immediately
before the existing Metal commit. It observes the existing command buffer and
adds a completion handler; it creates no queue, buffer, encoder, marker draw,
extra submit, synchronization wait or replacement rendering path. Upstream
commit/release/error behavior is retained. Queue-idle and surface-presentation
marker paths are excluded. The observer is disabled by default and requires an
explicit versioned callback registration from the fresh host.

Apple's [completion-handler API](https://developer.apple.com/documentation/metal/mtlcommandbuffer/addcompletedhandler(_:))
must be registered before commit and is called after the buffer finishes. The
[GPU timestamp API](https://developer.apple.com/documentation/metal/mtlcommandbuffer/gpustarttime)
is read from that callback. These observations describe the actual host command
buffers used by MoltenVK, independently of the guest's pixel receipt. They are
not game frames or a frame-rate measurement.

The host starts observation only for a fresh guest run after verifying the
framework's executable identity. Its process-lifetime callback context avoids
dangling references. A serialized ledger is capped at 256 observations; errors,
duplicates, unknown callbacks, wrong identity, overflow and pending work prevent
acceptance. After engine completion, it allows up to two seconds for pending
callbacks to drain. At least two successful native completions with valid GPU
execution timestamps must accompany valid guest shader pixels. The structured
native receipt is nonce-bound and includes all bounded samples. Neither a file
open nor a queue-idle marker can establish this acceptance.
