# Linux image import diagnostic 4000019

This change corrects the image format at every boundary. Package and phone acceptance are separate; this source document does not establish phone success.

## Pinned upstream cause

Linux 6.12.111 [`virtio_gpu_user_framebuffer_create`](https://github.com/gregkh/linux/blob/v6.12.111/drivers/gpu/drm/virtio/virtgpu_display.c) returns `-ENOENT` for ABGR8888. It accepts host XRGB/ARGB; the [primary plane](https://github.com/gregkh/linux/blob/v6.12.111/drivers/gpu/drm/virtio/virtgpu_plane.c) advertises only host XRGB8888. ARGB is the cursor format. This is a colour-format rejection, not proof of a missing imported buffer.

On little-endian ARM64, use Vulkan B8G8R8A8_UNORM (44), a DRM XRGB8888 framebuffer (875713112), virtio B8G8R8X8_UNORM (2), and Metal BGRA8Unorm (80). Render and export both use BGRA, so `vkCmdCopyImage` preserves the correct bytes. The diagnostic alpha is 255; primary scanout ignores this byte. Do not relabel RGBA bytes as XRGB. The [virtio UAPI](https://github.com/gregkh/linux/blob/v6.12.111/include/uapi/linux/virtio_gpu.h) supplies the format values.

## Changes and verification boundary

- Keep the ordinary offscreen Vulkan gate on RGBA. Its prior results do not accept image import.
- Query and create the export image with the same explicit DRM LINEAR modifier and BGRA format. Preserve dedicated allocation, exact row pitch/offset, fences and external queue ownership.
- Use a shared production framebuffer helper with XRGB. Emit resource ID, GEM handle, blob memory type and actual layout before framebuffer creation.
- Require matching Vulkan/DRM/virtio/Metal formats and channel order in both native and independent image receipt checks. Verify every pixel of two distinct phases. Channel sums alone cannot detect swapped red/blue.
- Compile and exercise the actual shared byte checker over 1,843,200 synthetic pixels, including swapped-channel rejection. These fixtures are not GPU evidence.
- Boot the pinned Linux kernel under hosted ARM QEMU. A CPU dumb-buffer control must reject ABGR with errno 2, create XRGB through the production helper and release it. This control never claims Venus image export, native memory import or presentation.
- Preserve missing-device, missing-3D and software-renderer rejection controls, native ownership/lifetime tests, physical ARM64 iOS compilation, complete source provenance and private device-log exclusion.

Reuse the unchanged source-built QEMU native scanout engine and MoltenVK completion observer. Publish their complete corresponding sources and notices with the package. QEMU TCG is software system emulation, not hardware virtualization. Vulkan-to-Metal is the graphics translation path. FEX and Proton are later CPU/API compatibility components.

## Required phone acceptance

Install the independently verified 4000019 prerelease with iLoader. Start a fresh app process, enable JIT using the app's StikDebug button, pass the ARM64 JIT check, then run Linux image import gate once. Keep the app foreground. Share the device report and recovery logs if needed.

Passing requires two Linux export resources joined to two native Metal consumers, exact layout/device identity, zero pixel mismatches, completed GPU commands and release of both images. The result still cannot establish visible presentation, SteamOS desktop, Steam ARM, FEX/Proton games, Steam startup time or Hollow Knight FPS. A later presentation gate must prove drawable completion and frame pacing on the phone.
