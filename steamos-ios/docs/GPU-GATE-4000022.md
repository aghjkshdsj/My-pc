# Build 4000022: scheduled screen presentation and lifecycle evidence

The fresh host tests a Core Animation transaction route for the same two real,
immutable Linux textures. The GPU command buffer is committed first. Its
scheduling callback dispatches to the main thread, checks the active surface,
and calls the drawable's present method within a transaction. No GPU scheduling
or completion wait runs on the main thread. The prior command-buffer presentation
route is replaced for this diagnostic.

Apple documents [presentsWithTransaction](https://developer.apple.com/documentation/quartzcore/cametallayer/presentswithtransaction)
for synchronizing Metal with surrounding UI. With that property enabled, it
requires GPU scheduling before drawable presentation and excludes the command
buffer's presentation convenience method. The [scheduled callback](https://developer.apple.com/documentation/metal/mtlcommandbuffer/addscheduledhandler(_:))
provides that scheduling observation without blocking UI. This is a documented
implementation choice, not proof of a phone-specific root cause or a measured fix.

## Measurements and acceptance

New schema2 screen records include real scheduling/enqueue/callback host clocks,
the callback's actual presentedTime, a separate later query of the same drawable,
main-thread/application-state observations and the selected layer route. The
[actual display timestamp](https://developer.apple.com/documentation/metal/mtldrawable/presentedtime)
must still be positive and ordered after GPU completion and enqueue. Zero in the
callback is preserved; a later API query or CPU callback clock cannot replace it.
These records do not establish animation, frame pacing, game FPS or remote
attestation. Old schema1 acceptance requirements remain intact.

Lifecycle capture records up to 32 reason/time/state observations. Resigning
active, background entry, drawable size changes or losing the window invalidate
an active run. A screenshot notification is recorded without itself invalidating
the run. Completed sessions stop accepting new lifecycle events, and an actual
interruption remains sticky. Source and scheduled-presentation rejections are
saved as durable stages. The final UI explains preserved image import and GPU
draws separately from incomplete display timing.

GPU completion joins actual presentation or an explicitly aborted presentation
exactly once. Cancellation cannot retire a still-running GPU consumer. Imported
source textures and drawable ownership remain retained by completion handlers,
including timeout paths. One consumer may be in flight and the drawable pool is
limited to two. The two source pixel readbacks remain correctness diagnostics;
there is no drawable CPU readback or host-generated substitute.

A build21-only failed-screen consistency mode checks the original failed report,
preserved Linux/guest/native Metal/import controls and zero callback timestamps.
It never rewrites status or accepts display timing, animation or games. Private
owner inputs and analysis remain excluded from uploads and release artifacts.

## Preserved execution and remaining work

The exact previously verified kernel, initramfs, engine closure and MoltenVK
observer pins are unchanged. CPU execution is QEMU TCG software system emulation.
Native Metal graphics do not establish hardware virtualization. Fresh host code
uses MIT; QEMU/Linux/BusyBox GPL, LGPL and dependency licenses still apply and
full corresponding sources accompany a verified prerelease. No Valve client or
game content is bundled.

Continuous guest animation, steady-state producer/consumer buffers, WSI/compositor,
SteamOS desktop/Game Mode/Steam ARM/CEF, FEX/Proton, input/audio/downloads/overlays/
plugins and sustained performance remain unfinished. The requested Linux
architecture and archive/blueprint coverage remain selected.
